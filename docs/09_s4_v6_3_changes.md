# S4 — V6.3: إصلاحات عامة لنمط الفشل (مش لقصة معينة)

السبب: التشغيلات المتكررة على نفس المدخلات بتدي نتايج مختلفة (i3: 4.11 مرة و4.44 مرة)، والفشل بيتنقل من مشهد لمشهد. التعديلات دي مش بتعرف أي موضوع أو شخصية.

## 1. إصلاح مقيّد بالمشاهد (`pipeline/repair.py`)
- بعد كل محاولة فاشلة، الكود يحدد المشاهد المعنية: من تفاصيل الفحوصات (مثل `s03_l02`) ومن `scene_id`/`line_id` في ملاحظات الـ Critic والـ audit، مع المشهد السابق واللاحق (لأن إصلاح الـ continuity غالبًا بيكون جنب السطر المذكور).
- فشل شامل (مدة، حصة الراوي، عدد المتكلمين، تغطية المفاهيم، must مش plot_tool، نسبة الشرح، درجات منخفضة بدون مكان محدد) = الكاتب حر في السكريبت كله.
- في المحاولة التالية، أي مشهد خارج النطاق بيرجع زي ما كان بالكود (حتى لو الموديل غيّره)، والـ prompt بيقول للكاتب أي مشاهد مفتوحة وأيها مقفولة (`REPAIR SCOPE`).
- لا بيتقفل شيء لو عدد المشاهد اختلف، أو لو مشهد مقفول محتاج متكلم الكاتب شاله.

## 2. فحص continuity ميكانيكي (`prompts/s4_continuity.md`)
- مرحلة صغيرة قبل الـ Critic: تبني جدول حالة (الأشياء والأعداد بعد كل سطر راوي) وتقارن بيه كل ادعاء من شخصية. ما بتشوفش نص الدرس ولا المفاهيم، بس السكريبت.
- ملاحظة `major` لازم تذكر سطر موجود فعلًا (غير كده بتتجاهل). لو فيه major: المحاولة بتفشل ونسيب الـ Critic (توفير tokens) إلا في آخر محاولة. القبول بيحتاج الـ Critic والـ audit الاتنين.
- فشل الـ audit نفسه (قطع الرد، schema غلط) ما بيفشّلش المحاولة، بيتسجل كـ minor.
- الإعدادات: `S4_CONTINUITY_AUDIT=0` يقفله، `S4_CONTINUITY_MAX_TOKENS` (6000).
- التكلفة: نداء إضافي لكل محاولة وصلت للـ Critic.

## 3. سجل تشغيلات مجمّع (`pipeline/run_log.py`)
- `scripts/run_s4.py` بيكتب صف لكل محاولة وصف لكل تشغيلة في `logs/s4_runs.jsonl` (القواعد اللي فشلت، فئات الملاحظات، الدرجات، المشاهد المقفولة، tokens لكل محاولة). مفيش نص قصة ولا prompts.
- `uv run python scripts/summarize_runs.py` يطبع: نسبة القبول لكل فكرة، أكتر القواعد فشلًا، أكتر فئات الملاحظات، متوسط الدرجات، متوسط الـ tokens.
